## EM-004 — Listing audio processes (2026-10-14) ✅

### What works
- `kAudioHardwarePropertyProcessObjectList` enumerates ~36 audio process objects; PID, `kAudioProcessPropertyBundleID`, `IsRunningInput/Output` read correctly.
- **Process-list listener fires reliably** — Teams quit/relaunch produced `process_removed`/`process_added` events within ~1–5 s.
- Owning-app attribution via executable path (outermost `.app`) works for helpers.

### ⚠️ Key finding: per-process state listeners do not fire
- Listeners on `kAudioProcessPropertyIsRunningInput` / `IsRunningOutput` registered without error but **never fired** on macOS 26.6.2.
- Every mic/output change (Chrome, Teams, corespeechd) was caught only by the 1 s poll.
- **Design impact:** detection must not rely on per-process listeners. Use:
  1. process-list listener (works) for add/remove,
  2. device-level `kAudioDevicePropertyDeviceIsRunningSomewhere` listener as an optional re-scan trigger (*inconclusive so far* — 10 s test run had no device state change: Chrome and corespeechd kept the devices running; `processes` keeps logging device callbacks, so EM-007 runs will settle it),
  3. 1 s poll of process input/output state as the guaranteed path (cheap: ~36 objects × 2 property reads/s).
  1 s latency is irrelevant given the 5 s start debounce.

Observations:
- Teams call audio (mic **and** output) runs in the **main process** `com.microsoft.teams2`, not a helper → capture tap must include at least the main process; include all `com.microsoft.teams2*` processes to be safe.
- Teams processes: `com.microsoft.teams2`, `.helper` (×3 WebView), `.modulehost`, `.notificationcenter`.
- **Mute does not release the mic** → mute will not end a session (good).
- Mic ON is the clean start signal; mic OFF is the clean end signal. Helper output alone is *not* a call signal (stays on after the call).
- In an earlier run (12:26) MSTeams had mic+output on — call state at the time unknown; re-check idle behaviour in EM-007.

### Other processes to ignore
- `com.apple.CoreSpeech` (`corespeechd`) — Siri/voice trigger; toggles mic on/off on its own. Never a meeting app.
- `com.google.Chrome.helper` — browser audio (YouTube etc.); only relevant for Phase 2 browser meetings.

### Other notes
- Chrome keeps its output stream open for a while after YouTube is paused (stayed on through a 10 s run; released ~30 s later in an earlier run). Another reason output state alone can't signal a call.

### Decision (EM-004)
Poll-based state (1 s) + process-list listener is the **baseline detection mechanism**; device listener is a latency optimisation only if EM-007 shows it fires. Technical Design §6.1/§6.3 to be updated in EM-008.

## EM-005 — Process-tap capture to WAV (2026-10-14) ✅

- `capture --app chrome` tapped 3 Chrome processes (`com.google.Chrome` + 2 × `com.google.Chrome.helper`) via `CATapDescription` stereo mixdown → private aggregate device (clock = MacBook Pro Speakers) → IOProc → Float32 WAV.
- Tap format: **48 kHz, 2 ch, Float32, interleaved**.
- System Audio Recording permission: granted on first capture; no virtual driver needed.
- File analysis (2 runs, 14–16 s): continuous signal, peak −5 / −7.5 dBFS, no clipping, **no dropouts mid-stream**.
- **Start-up gap:** first **47–307 ms** of each file is digital silence while the tap/aggregate device spins up → in production, start capture during the *Candidate* state (TD-4) so this gap never lands in the meeting; never start capture only at the moment recording is confirmed.
- Aggregate/tap setup takes ~25 ms; teardown is clean (no lingering devices).
- Note: CATapDescription created via a 2-function ObjC shim (`TapShim`) taking `NSArray<NSNumber *>`; keep this pattern (or verify the Swift overlay signature) in production.

## EM-006 — Real call capture

### Microsoft Teams (free, Meet now, Mac + phone guest) — 2026-10-14 ✅ capture works
- `capture --app teams` tapped **5 processes**: `com.microsoft.teams2` (MSTeams), `.modulehost`, 3 × `.helper` (WebView / WebView Helper).
- 31.4 s recorded, 2943 IO callbacks, **0 empty callbacks** — Teams keeps its output stream alive during silence (≈ −70 dBFS comfort noise), unlike Chrome.
- Peak −1.9 dBFS, no clipping; only the usual ~40 ms start-up gap.
- **L/R correlation = 1.000** → call audio is mono duplicated to stereo → store the system track as **mono** (halves size, matches TD design).
- Remote voice segments clearly present (speech-band energy ratio 0.6–0.98 in talk sections).
- 16–25 s: loud, wide-band (non-speech) content — music. *To confirm:* whether it was music played on the Mac (would mean isolation failed) or picked up by the phone's mic from the Mac speakers and sent back through the call (acoustic loop — expected, not a capture bug).
- Detection timeline: still to correlate with `processes` CSV (EM-007).

### WhatsApp Desktop (voice call to another person) — 2026-10-14 ✅ capture works
- `capture --app whatsapp` tapped **2 processes**: `net.whatsapp.WhatsApp` (main) and **`net.whatsapp.WhatsApp.ServiceExtension`** (separate extension process, likely the call engine) → always include all `net.whatsapp.WhatsApp*` processes.
- 31.4 s, 2940 IO callbacks, 0 empty; peak −1.0 dBFS, no clipping; ~36 ms start-up gap.
- **L/R correlation = 1.000** → mono, like Teams.
- Content is speech-only (speech-band ratio 0.8–1.0) and **band-limited: ~0 energy above 8 kHz** → wideband voice codec; 16 kHz mono storage loses nothing for STT.
- Silence handling differs from Teams: WhatsApp sends **exact digital zeros** (e.g. 4–6 s) while still delivering callbacks; Teams sends ≈ −70 dBFS comfort noise; Chrome stops delivering frames entirely. → The writer must treat all three as normal (VAD + timeline gap-fill).
- No music/other-app content detected in the file.
